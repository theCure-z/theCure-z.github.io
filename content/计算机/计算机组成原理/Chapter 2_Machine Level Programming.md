### 数据传送指令-mov 类

mov 类指令由四条指令组成:movb、movw、movl、movq,执行相同的操作,但是数据大小分别为 1 字节 （byte）、2 字节（word）、4 字节（double word）、8 字节（quad word）

![movq指令](https://cdn.nlark.com/yuque/0/2025/png/58377233/1763101900771-3c533c20-b636-4146-a071-3cfd74840af1.png)

movq指令提供5种在不同操作数之间交换数据的功能，其中立即数不能作为交换目的，因为是常数没有意义，且内存与内存之间无法交换，需要通过DMA或者以内存-寄存器-内存路径完成。

### leaq指令

与movq类似，但其不依赖于内存处的值，而是内存地址本身的运算与运用
movq (%rdi, %rdi, 2) , %rax：将3*%rdi的内存处的值赋给%rax
leaq (%rdi, %rdi, 2), %rax: 将3*%rdi赋给%rax
salq $2, %rax：将%rax左移两位，即地址扩大四倍
通过leaq和salq，将rdi的地址扩大了12倍

## 过程

假设过程P调用过程Q，过程Q执行后返回过程P，则需要多个机制维护：

1. 传递控制，在进入Q时，PC需要被设置为Q的代码起始地址，在返回P时，PC需要被设置为Q的下一条代码

2. 传递数据，P必须能向Q提供一个或多个参数，Q必须能向P返回一个值

3. 分配和释放内存，Q要为局部变量分配空间，返回时要释放空间

### 栈帧

![栈帧示意](https://cdn.nlark.com/yuque/0/2025/png/58377233/1763368189282-b3818441-8d88-4460-b90e-a3dfc692f9fe.png)

所有栈帧分布在同一块栈空间中的不同区域上，所以栈空间只有一块，只是将他划分成不同栈帧而已

调用函数创建栈帧后:

1. 一部分参数传入寄存器，多余参数压入栈底部
2. 压入当前调用函数的下一条指令地址也即返回地址

```bash
call foo
----------------
可以看做等价
push rip_next //压入当前指令(PC)的下一条
jmp foo //跳向foo
----------------
或者更详细点
push实现
rsp -= 8 //栈顶指针向下移8个字节64位
*(rsp）= rip_next //栈顶指针存入下一条指令
rip = foo //当前PC设为foo
----------------
不过这都是效果展示，实际上call是原子指令无法被拆分
且rip_next是一个拿不到的指令
```

3. 接下来进入栈帧真正的数据部分，主要做几件事

+ 压入%rbp：%rbp代表基地址，即上一个栈帧的底部，假如从 main 进入 foo，那么在 foo 的栈帧中压入 main 栈帧的基地址，为什么压入上一个栈帧的基地址原因很简单，在退出函数后该栈帧被舍弃，我们需要定位到上一个栈的起始位置

![画板](https://cdn.nlark.com/yuque/0/2026/jpeg/58377233/1777536847458-92cdbf24-882b-4b5c-bf03-81c267d3457d.jpeg)

+ 建立当前栈帧：我们已经压入了上一个栈的基地址，那么需要更新当前栈的基地址，指向刚刚存入的%rbp 处，刚刚存入的地址起始就是栈顶的位置，所以将当前栈顶%rsp->%rbp

![画板](https://cdn.nlark.com/yuque/0/2026/jpeg/58377233/1777536813451-6873de00-3711-47d0-bbd0-d0ff5a23b8e3.jpeg)

+ 为栈分配内存空间：将栈顶指针减去分配内存空间，保持基地址不变

![画板](https://cdn.nlark.com/yuque/0/2026/jpeg/58377233/1777536797381-14e769f7-c701-460c-a7f8-bdbd9a823197.jpeg)

```bash
1.压入%rbp
pushq %rbp
----------
2.建立当前栈帧
movq %rsp, %rbp
----------
3.分配空间
subq $32, %rsp
```

4. 退出阶段：

+ 恢复栈帧到当前栈基地址位置，当前栈帧中声明的变量直接抛弃，不用清空
+ 恢复上一个栈基地址
+ 返回

```bash
1.恢复至基地址
movq %rbp, %rsp
----------
2.弹出存入的上一个栈帧基地址，并赋给%rbp
popq %rbp
----------
3.返回
ret
```

# 数组分配与访问

对于数据类型 T 和整数 N，声明如下 :

`T A[N]`

这个声明有两个效果,首先,在内存中分配一个 L*N 字节的连续区域,L 为数据类型 T 的大小,其次引入标识符 A,可以通过 A 表示指向数组开头的指针 $ x_a $.最后数组元素 i 会被存放在地址$ x_a+L*i $的地方
当我们创建嵌套数组时,数组的分配和引用一般也是成立的,例如声明:

`int A[5][3]`

等价于创建一个 R*C*L 字节的连续区域:

`typedef int row3_t[3];row3_t A[5]`

通常来说,对于一个数组:

`T D[R][C]`

他的数组元素 `D[i][j]` 地址为:

` &D[i][j]=$ x_d+L(C\times{i}+j) $ `

实际上对于一个 C 列的数组,使用 (C-1)*L 可以代表数组的最后一个数据,而 C*L 代表了下一行数组的开头,在二维数组中,将基地址加上 i*C*L,代表了将基地址向下偏移 i 行然后再使用一维数组的地址索引方式

# struct

struct 声明一个数据类型,将不同类型的对象聚合到一个对象中,结构的所有组成部分存放在内存中一段连续的区域内,而指向结构的指针就是结构的第一个字节的地址,编译器维护相关信息记录每个字段的字节偏移.

![](https://cdn.nlark.com/yuque/0/2026/png/58377233/1776760521922-75738d67-7635-4a1a-a658-b5db478a6b02.png)

字节间对齐:
原则为 x 字节的数据地址开头必须为 x 的整数倍,在此例中,使用 3 个字节在 c 后使得 int 数组开头地址为 4 的整数倍,使用 4 个字节在 int 数组后使得 double 数据开头为 8 的整数倍
原因:机器倾向于一次性读取 64 个字节的内存数据,如果一个数据被分配至两个数据块会导致多余处理步骤

![](https://cdn.nlark.com/yuque/0/2026/png/58377233/1776761108611-b38c497d-67d5-4956-a47a-d611905f4f7f.png)

尾部对齐:
必须保证结构体长度为最长数据块的整数倍,否则在使用结构体数组的时候仍然无法保持对齐

![](https://cdn.nlark.com/yuque/0/2026/png/58377233/1776761219200-6d1fed4e-6213-465e-8881-fd66a8600659.png)

不同的数据声明方式会导致结构体使用不同的对齐方案,节省或浪费空间,将大块数据放在头部小块数据放在尾部

64 位地址意味着每个地址都由 8 个字节组成,总共能产生 2^64 个地址,而每个地址对应着一个字节的数据,意味着需要 2^64 个字节的内存才能将地址使用完,不过操作系统一般限制只使用其中的 47 位也即图中的 0x7FFFFFFFFFFF

Q1:地址空间使用了 47 位数,每个地址对应一个字节,假如我的内存条没有这么大空间怎么办
A1:不是每个地址都有对应的内存空间,没有分配内存的地址是没有意义的

Q2:在地址空间中连续的两个地址对应的内存上的数据位置也是连续的吗
A2:有可能不连续,内存上的空间按页管理,如果数组的相邻两位 a[n] 和 a[n+1] 被分配到了一页的尾和零一页的头,那么就会出现两个内存数据地址相邻但是位置不相邻的情况

栈位于地址空间最顶端,向下生长,通常大小为 8MB,可以在 linux 中用 limit 指令查看,如果使用栈外的地址空间寻址会发生段错误

data 存储声明的全局变量

shared-libraries 类似 text 部分,不过存储的是动态库的代码

# 栈溢出

![](https://cdn.nlark.com/yuque/0/2026/png/58377233/1776840478743-4a091d8c-9d3f-4f16-8aef-dc47dfe45660.png)

使用 gets 类似函数处理输入字符时可能出现的攻击行为，通过将字符串修饰为攻击代码+填充段 +返回地址的形式，可以覆盖原本位于栈帧中的函数返回地址，在退出栈时，一般使用指令`ret`，意思是提取$rsp 处的 8 个字节作为$rip，通常来讲，这里一般存储的是进入函数时的下一条指令地址`$rip+n`，这样在退出函数时取出进入函数时存储的地址才能保证退出到正常的位置，<font style="background-color:#FBDE28;">问题在于：通过栈溢出，可以修改返回位置至栈上 </font>，反编译通过 section 能区分栈上数据和代码数据，但 CPU 运行时只关注当前指令 $rip，这导致如果栈上的临时数据偶然组成了一条有意义的指令的话，CPU 不会分辨这是 data 部分的数据还是 text 部分的数据，会将栈上数据辨别成代码并执行（当然通常下会将栈上数据标注为不可执行区域）。

解决方案:
1. ASLR 随机缓冲区分配会对栈上的地址进行随机分配无意义空间导致每次进入程序时地址都不一致
2. 使用有保护的函数 fgets
3. 通过编译器的 canary 保护来完成预防
4. 通过将栈上的代码属性修改为不可执行来防止注入

---

上面的攻击使用的是**将返回地址改为栈上注入代码的地址**来完成攻击，但是假如使用栈随机化，即每次栈在地址空间中是随机的怎么办呢？此时我们无法得到我们注入的代码在哪，更难的是，假如将栈空间注释为不可执行，此时即使我们凑巧猜中了注入代码的地址，让$rip 指向了栈上空间，由于其不可执行，程序会抛出 segmentation fault 段错误，导致攻击失败，所以通过注入字符来充当攻击代码就完全失效了。

有没有其他的攻击办法呢？

```cpp
unsigned addval_273(unsigned x)
{
    return x + 3284633928U;
}

00000000004019a0 <addval_273>:
  4019a0:	8d 87 48 89 c7 c3    	lea    -0x3c3876b8(%rdi),%eax
  4019a6:	c3                   	ret    
```

观察上面的函数，其汇编如上所示，编译器如何知道一条命令的？因为编译器会根据查表来判断一条命令有多长，从而不会将 `4019a6 c3 ret`指令混在 lea 中，这是优点也是缺点，这导致如果在进行某些特定的数学运算的时候，某些奇妙的 MAGIC NUMBER 会排列成一条大命令中的小命令，例如以下例子

```cpp
4019a0:	8d 87 48 89 c7 c3
4019a3: 48 89 c7 c3 mov %rax, %rdi; ret
```

本来 lea 是从`4019a0`处的 6 个字节组成的指令，但由于其运算数字巧合的在命令中组成了`48 89 c7 c3`代码，而`48 89 c7`正是 `mov %rax, %rdi`，`c3`则是`ret`，这样一来代码完全颠覆了原先的`lea`的意思，更震惊的是我们完全没有注入任何执行的代码，而只是使用了源代码中的漏洞，这样的代码中的小块不同含义的代码被称为 gadget
到这就一目了然了，我们只需要将缓冲区溢出时替换为我们能找到的 gadget 的地址，让`ret`从一个函数的中部开始执行，就能达到攻击的目的，这种攻击方式被称为 ROP （Return-oriented Programming 面向返回的）攻击
